# 予約入口 3パターン — 改善検討メモ

> **更新メモ**: 本書の P0/P1（上書き確認・数量/時刻ブロック・履歴snapshot・preferences・エラー辞書）はおおむね実装済み。ただし**ポップアップの最終方針は「編集・再予約」ではなく「ビジュアル確認＋予約取り消し」**に変更された（[3-pattern-sync-redesign-design.md](3-pattern-sync-redesign-design.md)・[pattern-2-popup-reservation-design.md](pattern-2-popup-reservation-design.md)）。また、URLパラメータ必須の扱いと詳細コンソールの取り消し経路には実装上の懸念が残るため、最新の確認結果は [current-implementation-review.md](current-implementation-review.md) を参照。

## 結論

3パターン化の方向性は良い。ユーザーの状況別に入口を分けつつ、最終的な予約保存と実行は既存の `te_job_v1` / alarm / content script 実行へ集約できている。

ただし、入口が増えるほど「どこで編集した内容が正か」「既存予約を上書きしてよいか」「数量0や時刻未確認で予約してしまわないか」が使いにくさや事故につながる。改善の中心は、派手なUI追加ではなく、3入口に共通する安全弁と役割分担を明確にすること。

推奨する体験の優先順位:

1. **ページ内**: 初回の新規予約に最適。対象ページ上で最短予約。
2. **ポップアップ**: 現在の予約のビジュアル確認・取り消しに最適。
3. **詳細コンソール**: 詳細設定、履歴、失敗原因、再予約に最適。

## 改善優先度

| 優先度 | 改善 | 理由 |
| --- | --- | --- |
| P0 | 予約保存の安全弁を共通化する | パターン1/3から `SAVE_JOB` できるため、意図しない上書きを防ぐ必要がある |
| P0 | 数量0・時刻未確認では予約できないようにする | 現状の「パルスで促す」だけでは誤予約を止められない |
| P0 | 実行履歴は job snapshot を保存する | 実行中に設定が変わると履歴が別内容で記録されるリスクがある |
| P1 | 詳細設定を preferences 化する | パターン1/2が毎回既定値に戻すと、ユーザーの運用意図を壊す |
| P1 | パターン1は自動展開しすぎない | ページ上UIは便利だが、購入フォームを邪魔すると逆効果 |
| P1 | エラー表示を全入口で共通辞書化する | 同じ失敗が入口ごとに違う言葉で出ると混乱する |
| P2 | 旧設計書との位置づけを明記する | `ticket-page-entry-ux-design.md` と新パターン1の責務が一部重なる |

## 1. 予約保存の安全弁

現行の `SAVE_JOB` は単一の `te_job_v1` を上書きする。パターン1（ページ内）とパターン3（詳細コンソール）から予約できるため、ユーザーが知らないうちに別ページの予約を置き換えるリスクが高くなる。ポップアップは `SAVE_JOB` を送らない。

推奨仕様:

- 同じ `jobId` の更新: そのまま許可。
- 予約が存在しない: そのまま許可。
- 既存予約と別URL・別jobIdの新規保存: 明示確認が必要。
- SW側でも確認済みフラグがない上書きを拒否する。

追加フィールド案:

```js
{
  job,
  replaceMode: "create" | "update" | "replace",
  expectedPreviousJobId: "job_...",
  replaceConfirmed: true
}
```

SWは、既存jobがあるのに `replaceConfirmed` がない場合、`E_REPLACE_CONFIRM_REQUIRED` を返す。UIだけで防ぐのではなく、バックエンド側でも守る。

UIコピー:

```text
別の予約が実行待機中です
現在の予約をこのページに切り替えますか？

現在: {existingEventTitle}
新規: {newEventTitle}

[切り替える] [キャンセル]
```

## 2. 数量0と時刻未確認は予約不可にする

各設計書では「数量0なら amber パルスで促す」となっているが、これは注意喚起であって防止ではない。数量0で `SAVE_JOB` できると、当日にチケットを選ばずカート投入ボタンだけ押す可能性がある。

推奨仕様:

- `ticketPlans.some(plan.targetQty > 0)` が false の場合、予約ボタンは disabled。
- disabled 理由をボタン直下に表示する。
- SWの `sanitizeJob()` でも targetQty > 0 が1件もないjobを拒否する。
- 実行時刻は「自動入力された値」では完了扱いにしない。ユーザーが確認または変更した時点で完了にする。

コピー:

```text
予約するには、1枚以上の数量を設定してください。
```

```text
実行時刻を確認してください。
```

時刻の扱い:

- 新規予約では `現在+10分` を仮入力してもよいが、`未確認` 状態にする。
- 既存予約の編集では保存済み時刻を確認済みとして扱う。
- ページ内パネルでは、時刻入力欄を開いた/変更した/確認ボタンを押した時点で確認済みにする。

## 3. 実行履歴は job snapshot を保存する

パターン3の履歴設計では `RunRecord` に `eventTitle` / `targetUrl` / `ticketPlans` / `triggerAtJst` を保存する方針になっている。ただし現行の content script が返す `EXECUTE_RESULT` には、これらの完全なjob情報は入っていない。

現行に近い実装でSWが「現在の `te_job_v1`」を読んで履歴化すると、実行中にユーザーが別予約へ変更した場合、履歴が別内容で記録される可能性がある。

推奨仕様:

1. dispatch時点で `runId -> jobSnapshot` を保存する。
2. `EXECUTE_RESULT` 受信時に、その snapshot と result を結合して `te_runs_v1` にappendする。
3. snapshot が見つからない場合だけ、互換fallbackとして現在jobを参照する。

追加ストレージ案:

```js
te_active_runs_v1: {
  [runId]: {
    jobSnapshot,
    triggerEpoch,
    dispatchedAt,
    tabId
  }
}
```

または、`EXECUTE_REQUEST` に渡した `job` を content script の `runResult.jobSnapshot` に含めて返してもよい。ただしページ側から返るデータを信用しすぎない方針なら、SW側snapshotの方が堅い。

## 4. 詳細設定は preferences として分離する

パターン1は「詳細設定を出さず既定値」、パターン2は「保存済み値を維持、無ければ既定値」となっている。ここはユーザー視点では少し不安定。

例:

- 詳細画面で並列数を3にした。
- 次回、ページ内パネルから予約した。
- パターン1が既定値1で保存し、意図せず並列数が戻る。

推奨仕様:

- 詳細設定は `te_preferences_v1` として保存する。
- パターン3の詳細設定は「現在jobだけ」ではなく「今後の予約に使う既定値」を編集する。
- パターン1/2は `te_preferences_v1` を使ってjobを作る。
- 既存job編集時は job の詳細値を優先し、無ければ preferences を使う。

モデル案:

```js
{
  clickIntervalMs: 30,
  parallelTabCount: 1,
  requireAgreement: true,
  selectorOverrides: null
}
```

これで、簡易入口を使ってもユーザーの運用設定が保たれる。

## 5. パターン1は「控えめに出て、クリック後に展開」がよい

ページ内パネルは最も便利だが、最も邪魔にもなりやすい。特にチケットページでは、ユーザーは本来のフォームも見ているため、最初から大きなフォームを出すと圧迫感が出る。

推奨表示:

1. フォーム検出時: 小さなピル/ミニカードを右下に表示。
2. ユーザーが押す: 読み取り開始してフォーム展開。
3. 閉じる: タブ内では小バッジに縮小。
4. 同URL予約中: 小さなカウントダウンカードを表示。

初回カード:

```text
TicketEscape
このページを予約できます
[予約]
```

クリック後に初めて券種・時刻のフォームを出す。自動表示でフォーカスを奪わない点は現設計どおりで良い。

## 6. 「予約」の意味をUIで補足する

ユーザー向けに「予約」と言うのは短くて良いが、チケットサイトの「予約」と混同しやすい。初回だけは、何が起きるのかを短く補足した方が安心感が上がる。

推奨表記:

- 主ボタン: `予約`
- 補足: `指定時刻にこのページを開き、選んだ数量でカート投入します`
- 内部/詳細: `実行待機`

「予約する（実行待機）」は情報量が多いので、パターン1/2ではボタン文言を短くし、補足で説明する方が読みやすい。

## 7. エラー辞書を共通化する

各パターンにエラー文言があるが、実装時に入口ごとにばらける可能性が高い。`lib/shared.js` にエラーコード→ユーザー文言の辞書を持たせるとよい。

例:

```js
ERROR_MESSAGES = {
  E_FORM_TIMEOUT: "チケットフォームが見つかりません。購入ページを開いてから再試行してください。",
  E_TICKET_LIST_TIMEOUT: "フォームは見つかりましたが、券種を読み取れませんでした。ページの読み込み後に再試行してください。",
  E_TICKET_NOT_FOUND: "選択した券種がページ上に見つかりませんでした。もう一度読み取ってください。",
  E_SUBMIT_NOT_APPLIED: "カート投入が反映されませんでした。ページ状態を確認してください。",
  E_REPLACE_CONFIRM_REQUIRED: "別の予約が実行待機中です。切り替える場合は確認してください。"
}
```

詳細画面では原文 `errorDetail` も展開内に残す。ページ内・ポップアップではユーザー文言だけ出す。

## 8. 3パターンの役割をさらに明確にする

3つとも予約までできるため、ユーザーが「どれを使えばいいか」を迷わない表現にする。

推奨する役割コピー:

| 入口 | 役割コピー |
| --- | --- |
| ページ内 | このページをそのまま予約 |
| ポップアップ | いまの予約をすばやく確認・取り消し |
| 詳細コンソール | 履歴・詳細設定まで管理 |

パターン2は「新規URLから何でもできる場所」ではなく、「保存済み予約を素早く確認し、必要なら取り消す場所」と割り切れている。この判断は良いので、UIにも明確に出す。

## 9. 旧設計書との関係を整理する

`ticket-page-entry-ux-design.md` は「起動パネル → オプション画面」中心、`pattern-1-in-page-reservation-design.md` は「ページ内で予約完結」中心になっている。

このままだと実装時にどちらが正か迷うため、どちらかを明記する。

推奨:

- `ticket-page-entry-ux-design.md` の冒頭に「先行案。現在の正式方針は 3パターン設計」と追記する。
- または `reservation-entry-points-overview.md` に「旧docは背景資料、実装正は pattern-*.md」と明記する。

## 10. 推奨実装順

使いやすさと安全性を両立するなら、入口UIより先に共通基盤を固める。

1. **共通安全弁**
   - 数量 > 0 必須
   - 時刻確認必須
   - 上書き確認必須
   - エラー辞書
2. **詳細コンソール強化**
   - 既存画面なので実装・検証しやすい
   - `te_runs_v1` と job snapshot を追加
   - preferences を保存
3. **ポップアップのビジュアル確認化**
   - 保存済み予約のヒーロー画像・公演名・日時・券種・カウントダウンを表示
   - 編集・再予約・現在タブ読み取りは行わず、詳細コンソールへ引き継ぐ
4. **ページ内パネル**
   - まずは控えめな起動カード
   - 次に読み取り・フォーム展開
   - 最後にページ内完結予約

ユーザー体験だけを見るとパターン1が最も目立つが、実装リスクは一番高い。先に保存と履歴の基盤を固めると、ページ内パネルを追加した時の事故が少ない。

## 11. 受け入れ条件への追加提案

既存の各設計書に、以下を共通受け入れ条件として足すとよい。

1. 数量が1枚以上ない状態では予約保存できない。
2. 新規予約の実行時刻はユーザー確認がない限り予約保存できない。
3. 別URLの予約を上書きする場合、ユーザー確認なしではSWが拒否する。
4. パターン1/2/3のどこから予約しても、詳細設定 preferences が一貫して使われる。
5. 実行履歴には、実行開始時点の job snapshot が保存される。
6. 同じエラーコードは全入口で同じユーザー向け文言になる。

## 12. 実装確認で残った懸念

実装を正として docs を更新する一方で、次はコード側で方針確認が必要な点として残す（詳細は [current-implementation-review.md](current-implementation-review.md)）。

1. URLパラメータ必須の設計文言に対し、現行 SW は `isEscapeTicketPageUrl()` を保存/読み取り/dispatch の検証に使うため、URLパラメータ無しでも保存できる可能性がある。
2. 詳細コンソールの取り消しは、options 側で storage/alarm を直接 clear してから `CANCEL_JOB` を送るため、SW の単一経路にはまだなっていない。
3. `selectorOverrides.heroImage` は content 側の抽出では見ているが、SW の sanitize/preferences 永続化では保持されない。
4. `PAGE_DRAFT.tabId` は保存されるが、詳細コンソールの読み取りでは元タブへ直接送信せず URL 経由で SW に依頼する。

## まとめ

現在の3パターン設計は「入口の多様化」と「中核ロジックの共通化」ができていて、方向性は強い。改善するなら、UIを増やすより先に、共通安全弁・job snapshot・preferences・エラー辞書を入れるのが効果的。

特に P0 の3つ、つまり **上書き確認・数量/時刻の保存ブロック・履歴snapshot** は、使いやすさというより信頼性そのものに関わる。ここを設計に組み込めば、3入口はかなり安心して育てられる。
